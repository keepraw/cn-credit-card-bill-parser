# Large Ledger Reliability & Performance Optimization Report

基准来源：[PR #26](https://github.com/keepraw/keepraw-ledger/pull/26)，固定种子 `1263684657`。本次对照基于 main `37a603be`；所有测试均使用虚构数据，不读取或上传真实账单。数据库为实际 Chromium IndexedDB。生产依赖与锁文件未修改。

## 结论与合并建议

**合并建议：YES（测量不确定性经工程评估接受，Ready for Review；不自动合并）。** 备份、原子性、旧库升级与逐笔完整性测试已通过，所有完整性计数为 0。常规启动、编辑、搜索、排序和导入明显改善；100k JSON 导出中位数也改善。全量读取未得到可重复提速，主负载 +11.1%、独立读取 +2.7% 均如实保留在下文，不删除、不美化；2026-10-15 专项复查认定该差异既未证明稳定系统性退化，也不构成严格非劣效证明（混合 p≈0.14，独立 p≈0.48，范围完全重叠且有一个 After profile 更快），在系统级工作流总收益与 143 计数全 0 的前提下作为测量不确定性接受。本轮没有通过移除一致性读取保证来追求该微基准。全量读取仍需要 O(N) 的对象加载，不能将“减少全量读取次数”解释成消除这项成本。以下数据完整保留中位数及最小–最大范围，负改善值表示变慢。

本轮保留全部金融和审计字段，不更改 ID、fingerprint、occurrence、币种与金额规则、XLSX 格式、Golden JSON 或 Python retirement 边界。没有重建数据库、删除账本数据或通过导出导入替代升级；测试中的清空仅发生在独立合成 profile 中。

## 测量口径与可复现性

同一生成器、文件名、锁定依赖、机器、浏览器、生产构建及探针分别运行旧 main 和优化版本。机器为 Xeon Platinum 8370C，5 vCPU / 17.586 GiB RAM，Node v24.19.0；基准使用系统 Chromium，普通 E2E 使用 Playwright 安装的 Chromium。18k/100k 各进行 3 次独立 XLSX 导入和页面就绪测量，读取/刷新/编辑/筛选/排序各 5 次，JSON 实际下载各 3 次。未在计时期间并行运行其他测试。原先环境预装的 XLSX/Vitest 与锁文件版本不一致，正式结果使用 `npm ci` 后的版本；因此不能直接把 PR #26 的单组数值当成这次对照的 Before。

表中耗时单位为 ms，格式为**中位数 [最小–最大]**。React commit 使用 layout effect；UI 交互从实际捕获事件到两次 animation frame。`refresh`、真实下载 API 和保留的 pretty JSON 微基准是不同指标。3 次 fresh restore 与 6 次幂等 restore 分开统计。

Origin estimate 是 `navigator.storage.estimate()` 的估计。文件长度只统计隔离 profile 的 `Default/IndexedDB` 文件；allocated bytes 使用 `stat.blocks * 512`，包含文件系统分配、LevelDB 日志和历史条目。它们均不是 JSON 体积或精确索引大小。稳定索引对照在相同检查点关闭浏览器、只读重开，然后再次关闭测量。

[运行说明](../../web/scripts/large-ledger/README.md)提供独立压力测试命令。所有原始样本及来源哈希见 [large-ledger/](large-ledger/)；不把 100k 全套测试加入每次普通 CI。各阶段结果逐步取得；最终排序修正后重跑主性能对照及完整普通回归。已完成备份/索引样本的 AppStore、database、backup 文件哈希与最终代码相同；仅交易列表计算顺序随后调整。migration 的 schema/backup 源码相同，AppStore 的偏好复选框反馈修正与 database-only 升级路径无关。

## Backup Reliability（Phase A）

旧版允许导出 100k 的约 113.056 MiB pretty JSON，却用 32 MiB 上限拒绝恢复。本轮维持 Version 1 字段及 ZIP 条目，只改变内部处理和 JSON 空白：按约 64 Ki 字符块编码 UTF-8 Blob，ZIP 按块输出；成功导出和恢复应用相同资源规则。

| 资源 | Before | After | 依据 |
| --- | --- | --- | --- |
| 每个 JSON | 32 MiB | 128 MiB | 容纳已有 113.056 MiB 历史 pretty JSON；compact 导出保留所有字段 |
| ZIP 输入/输出 | 128 MiB | 256 MiB | 与最多 256 MiB 展开预算配套，实际输出也检查 |
| 总展开内容 | 256 MiB | 256 MiB | 保留总资源边界 |
| 每个原始文件 | 64 MiB | 64 MiB | 不放宽原始附件单项限制 |
| ZIP 条目 | 20,000 | 20,000 | 保留目录/路径/条目约束 |
| 数据记录 | 1,000,000 | 1,000,000 | 同时受字节/结构上限约束 |
| JSON 结构 | 无独立预检 | 深度 64；token 8M；container 2M | 在 JSON.parse 之前限制小字节对象/标量炸弹；导出同样检查 |

JSON 仍需整体 parse 和类型验证，不能称为流式解析。128 MiB 文本最多约 256 MiB UTF-16，另需对象图、当前 state、IDB clone、ZIP 原始字节及浏览器开销。实际 stress 的 Chromium **汇总 RSS 峰值 2.815 GiB**，测试 Node 峰值 1.254 GiB。汇总 RSS 会重复计算共享页；Node 包含生成/保留测试文件，不属于产品浏览器。字节/结构限制是受控资源预算，不能保证所有低内存设备都能恢复。100k 完整账本应视为桌面工作负载。

数据导出在一个 readonly transaction 中读取一致的财务快照，manifest 使用该快照。导出检查记录有效性、真实证据 SHA-256、实际字节及结构预算，超限抛错而不下载一个无法恢复的文件。恢复先完成解码、manifest/路径/哈希/类型检查，再在一个 rw transaction 中提交账单、交易、导入、设置和原始附件。2,000 条批次仍在同一个事务内，金融/身份冲突或晚期附件错误回滚全部写入。

## Performance Comparison（Phase B）

单条交易更新先在 rw transaction 中读取最新行、合并请求字段并成功提交，再用 functional state update 替换对应行。写入失败保持交易 state，后续操作仍可执行。小型 provider 队列把刷新与写入串行化，防止旧快照覆盖较新编辑；不构建额外账本缓存。复杂导入、恢复、清空继续使用完整刷新。

启动由两次快照读取改为一次。历史 Demo 清理成功后保存 O(1) marker；持久化 Demo 记录的已有入口原子地使 marker 失效。没有跳过旧库第一次清理，也没有扩大为 Demo 孤立附件清理。偏好设置保留原先即时复选框反馈，串行持久化失败回滚；交易与备注严格提交成功后更新。

## IndexedDB Optimization（Phase C）

版本从 Dexie v2 升至 **v3（native IndexedDB 30）**。保留 v1/v2 声明，通过正常 versionchange transaction 删除二级索引，没有业务数据 rewrite callback。六个 Object Store 和主键全部保留。

| 表 | 保留 | 删除 | 决定依据 |
| --- | --- | --- | --- |
| transactions | 主键 id；statementId | bank、transactionDate、postingDate、type、category、reviewStatus、isDemo、fingerprint、[bank+transactionDate] | 唯一实际二级索引查询是 restore 的 where(statementId).anyOf；其余生产筛选/排序/去重用完整数组与 Map，主键 bulkGet 不依赖它们 |
| statements | 主键 id | bank、cardLast4、cycleEnd、status、isDemo | 全量读取/primary key get/boolean cursor filter；没有索引 where/orderBy |
| imports | 主键 id | fileHash、importedAt、status、isDemo | 导入/清理/manifest 使用数组、主键和显式过滤 |
| attachments | 主键 fileHash | importId、importedAt | evidence 以 SHA 主键读写和全量 manifest 检查 |
| settings / reviewNotes | 原主键 | 无 | 没有二级索引 |

共删除 **20 / 21** 二级索引。3 个 isDemo Boolean 索引没有有效 Boolean key 条目；生产清理本来使用 explicit filter，删除不会改变匹配规则。指纹仍完整保存在交易对象中，算法和 occurrence 未改。若未来引入数据库范围查询，需先正式添加所需索引，不能假定这些索引仍存在。

### 原始数据与波动（ms）

### Dexie 只读事务、反序列化、GC/分配与负载顺序

- 只读事务：旧 `readSnapshot` 为三个隐式只读事务的 `Promise.all`，新为一个显式 `db.transaction('r', …)` 内的 `Promise.all`。前者 3 次事务创建/提交，后者 1 次；仅从事务开销看新路径应持平或略优，不能解释变慢。原生 `getAll` 同为单 readonly 事务，仅快 2.5%，已按原则放弃生产化。
- 反序列化：交易对象、账单、导入的序列化字节数在 v2/v3 对照中完全相等；100k 约 89.5 MiB JSON、118.5 MiB 备份字节，单个快照仍需 O(N) 对象加载约 1.6–1.8 s。存储层直接 `table.toArray()` 在受控对照中反而改善：18k 302.7→280.5，100k 1,707.3→1,597.1（约 6.5%），证明 v3 索引删除未使全表读取退化。
- GC/分配：混合负载在每次读取之间插入 `backupRead`（约 1.5–2.7 s）、`backupEncodeBlob`（After 出现 5,172.9 ms 离群，Before 最大 2,846.2）、`refresh`（约 1.5–2.1 s）。After 独立读取 SD 281.9 vs Before 67.1，混合 SD 345.0 vs 136.7，均为方差膨胀而非整体平移，符合大对象图 + 大字符串分配后的 GC/堆碎片特征；不能将 GC 定为已证明根因，仅记录为最可能的波动来源。
- 负载顺序：混合 +11.1% vs 独立 +2.7%；独立诊断刻意移除导出/筛选/刷新干扰后差异收窄至 43.2 ms。主表 5 样本全部来自 `performance-*-0` 单 profile，独立诊断覆盖 3 profile×7，覆盖度更高但仍是小样本。

### 实际意义：系统级读取成本下降

单次快照 +176 ms（混合）/+43 ms（独立）需与已实现的读取次数削减一起评估：启动由 2 次快照改为 1 次（100k 首次就绪 8,074.5→3,327.0，节省约 4,747 ms；其中读取成本从约 3.1 s 降至约 1.7 s）；单条编辑由每次 1 次全量读取降为 0 次（API 1,545.7→3.8，节省约 1,542 ms；自动化测试确认初始化仅 1 次、编辑 0 次）；100k 历史导入节省约 20,356 ms，确认/持久化/刷新节省约 19,976 ms。日常“打开+一次编辑+一次搜索+一次排序”的总节省为秒级，远大于单次快照百毫秒级波动。18k/100k 的筛选、排序、UI 搜索/排序、JSON 导出全部改善或持平（仅 100k 完整集合筛选 -8.6%、约 1 ms 量级）。
